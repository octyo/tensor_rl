## Tensor Networks in RL — Codebase Overview

### Research Question
When does low-rank tensor decomposition reduce parameters while maintaining or improving RL performance? The project uses **MiniGrid-Empty-5x5-v0** as the test environment and **Double DQN** as the agent.

---

### What Each Case Tests

| Case | File | What It Tests |
|------|------|---------------|
| 0 | `case0_baseline.py` | Standard DQN across hidden sizes — establishes `h128x128` (36,359 params) as reference |
| 1 | `case1_cp_layers.py` | Replace `nn.Linear` with CPLinear (rank-R factorized) — rank sweep [1,2,4,8,16,32] |
| 2a | `case2a_decomp_init.py` | All decomposition types (CP, Tucker, TT, MPS) initialized decomposed from ep 1 |
| 2b | `case2b_compress.py` | Train standard DQN → compress post-hoc via tensorly SVD, evaluate without fine-tuning |
| 3 | `case3_structured.py` | Treat obs as genuine `(7,7,3)` tensor → TTEmbedding/CPEmbedding/TuckerEmbedding |
| 4 | `case4_cnn.py` | Tensorized CNN: either decompose the linear head or the conv layers themselves |
| 5 | `case5_tensorized.py` | Full head-to-head comparison of all methods at matched ranks |
| 6 | `case6_mps.py` | True N-core Tensor Train (MPS) vs 2-factor CP at same rank |

---

### Key Architecture Pieces

**Tensor layers** (`sim/models/tensor_layers.py`):
- `CPLinear` — W ≈ factor_out · factor_in^T
- `TuckerLinear` — W = factor_out @ core @ factor_in^T
- `TTLinear` — 2-core Tensor Train
- `MPSLinear` — true N-core TT, auto-factors dimensions
- `TTEmbedding`, `CPEmbedding`, `TuckerEmbedding` — for structured `(7,7,3)` obs (Case 3)
- `CPConv2d`, `TuckerConv2d` — for CNN tensorization (Case 4)

**Agents** (`sim/agents/`): DQN, DoubleDQN (default), DuelingDQN

**Training loop** (`sim/cases/utils.py`): Creates env → network → agent → runs N episodes with ε-greedy, returns `(n_params, reward_mean, reward_std, solve_rate)`

### 2. Tucker is consistently broken at low rank, then recovers
Tucker fails completely at r2/r4 (10-14% solve) and the convergence curves show active **collapse** — it starts learning, then degrades. `tucker_r4` in case5 goes: 0.225 → 0.379 → 0.280 → ... → 0.057 → 0.113. Tucker seems to have a **rank threshold below which it becomes unstable**, not just weak.

### 3. Structured embeddings beat flat DQN despite fewer params — across ALL methods
In case3, every single structured embedding config (tt, cp, tucker at any rank) outperforms the flat standard baseline (77% solve). `tt_r2` hits 98% solve at 18,353 params (50% of standard). The flat baseline at 77% is the worst-performing "standard" across all cases, suggesting flattening the observation is actually hurting the agent.

### 4. CP has a sharp phase transition around rank 16
In case1 and case5: cp_r8 is unstable (74-81% solve, high variance), cp_r16 suddenly converges cleanly (95-96%, near-zero std). There's a cliff between r8 and r16 — rank 16 appears to be the intrinsic rank of this Q-function under CP. Below it: high variance, unreliable. At it: consistent and matches standard.

### 5. Tensorized CNN convolution layers completely fail
Case4's `tensorized_*` configs (CP/Tucker applied to Conv2d layers) plateau around 30% solve and the convergence curves **regress after episode 60** — they were learning then unlearn. Even with 300 episodes of training and 50 episodes fine-tuning, every compressed model collapses. ### Environments & Tasks
- **Harder maps**: MiniGrid-Empty-8x8 or 16x16 — the 5x5 task may be too easy (standard networks reach 95%+ in 100 episodes), meaning differences between methods get compressed into a small performance band. A harder task would spread the methods further apart and reveal true scaling behavior.
- **FourRooms or MultiRoom**: Requires sequential sub-goals, long-horizon reasoning — much more representative of where tensor structure would actually help.
- **Partially observable tasks**: MiniGrid already has a partial obs wrapper; the agent currently sees the full grid. Testing on true partial obs would stress the representation harder.
- **Continuous control (MuJoCo or LunarLander)**: State spaces are richer and Q-function is more complex — would test whether these findings generalize beyond discrete gridworld.

Your understanding is **partially right but not quite**. Let me clarify precisely — there are actually three fundamentally different CP implementations in the codebase, not the same one used in different contexts:

---

## The three CP implementations

### 1. Tabular CP (`cp_agent.py` — `CPGridQAgent`)

This is CP applied directly to the **Q-table itself**, not a neural network. The Q-function is represented as a 3-mode tensor:

```
Q[row, col, action] = Σ_r  A_row[r, r] · A_col[col, r] · A_act[action, r]
```

- **What it factorizes**: the Q-table (a 3D array of shape `rows × cols × actions`)
- **Environment**: a custom `GridWorld` (not MiniGrid) — a simple deterministic grid
- **Learning algorithm**: pure Q-learning with NLMS semi-gradient updates directly on the factor matrices — **no neural network, no replay buffer, no PyTorch**
- **Parameters**: `rank × (rows + cols + n_actions)` — e.g. rank=4 on 5×5 grid = `4 × (5+5+4) = 56 params`
- **Baseline comparison**: versus a full tabular Q-table (`rows × cols × actions = 100 params`)

### 2. CP in Case 1 / Cases 2a, 5 (`CPLinear` in `tensor_layers.py`)

This replaces the **weight matrices inside a neural network** with a CP factorization:

```
W[out, in] ≈ factor_out @ factor_in.T   (rank-R matrix factorization)
```

- **What it factorizes**: each `nn.Linear` layer's weight matrix (a 2D matrix, so really just a low-rank matrix decomposition)
- **Environment**: MiniGrid via neural network DQN
- **Learning algorithm**: Double DQN — the factors are PyTorch `nn.Parameter`s trained end-to-end with backprop, Adam optimizer, replay buffer
- **Parameters**: `rank × (in + out) + out` per layer — e.g. rank=8 on a 128×128 layer = `8×256+128 = 2176`
- **Baseline comparison**: versus a standard `nn.Linear` (128×128 = 16,384 params per layer)

### 3. CP in Case 6 (`case6_mps.py`)

This is **the same `CPLinear` as case 1** — identical implementation. Case 6 runs CP as a **comparison baseline alongside MPS**, to directly answer "does MPS beat CP at the same rank?" It's not a different CP; it's just that case 6 runs both methods side-by-side for a direct head-to-head.

---

## Summary of differences

| | Tabular CP (`cp_agent`) | Case 1 / 2a / 5 CP | Case 6 CP |
|---|---|---|---|
| **What's factorized** | Full Q-table (3D tensor) | Weight matrices (2D) | Same as case 1 |
| **Modes** | 3 (row, col, action) | 2 (in, out) — just low-rank matrix | Same as case 1 |
| **Learning** | NLMS semi-gradient, NumPy | Backprop through network, PyTorch | Same as case 1 |
| **Environment** | Custom GridWorld | MiniGrid | MiniGrid |
| **Comparison baseline** | Full Q-table | Standard `nn.Linear` | MPS at same rank |
| **"Rank" meaning** | CP-rank of Q-tensor | Rank of weight matrix factorization | Same as case 1 |

The tabular CP is the more theoretically pure application of CP decomposition — it factorizes the Q-function itself as a tensor. The neural network CP (cases 1, 2a, 5, 6) is using CP only to compress weight matrices, which is closer to standard low-rank matrix approximation than genuine tensor decomposition (since a 2D matrix has no higher-order structure to exploit).

User: But the mps is genuine tensor decomposition?

Claude: Yes, exactly — and that's the key architectural distinction in the whole codebase.

**CPLinear on a weight matrix is just low-rank matrix factorization:**
```
W[out, in] ≈ factor_out @ factor_in.T
```
It's two matrices multiplied together. There's no tensor structure — it's the same as truncated SVD. The "CP" name is technically correct (a rank-R CP decomposition of a 2D tensor is a sum of rank-1 matrices) but there's nothing genuinely multi-linear about it.

**MPSLinear is genuine higher-order tensor decomposition:**

The weight matrix `W[out, in]` is first **reshaped** into a higher-order tensor by factoring both dimensions into multiple modes:
```
in=128  →  (8, 4, 4)   — 3 input modes
out=128 →  (8, 4, 4)   — 3 output modes
W[out, in] → W[d_out0, d_out1, d_out2, d_in0, d_in1, d_in2]
```
Then a Tensor Train decomposition is applied across those modes, giving N cores connected by bond dimensions (rank):
```
W ≈ G_1[r0, d0, r1] · G_2[r1, d1, r2] · G_3[r2, d2, r3]
```
This is a genuine multi-linear factorization — the rank controls the bond dimension between cores, and the information flows sequentially through the chain. The weight is never explicitly a matrix during the decomposition; it lives in a higher-dimensional space.

**Why this matters for the results:**

This is likely why MPS outperforms CP so dramatically at low rank on Empty-5x5 (case 7: `mps_r2` = 95% solve vs `cp_r1` = 23% at matched ~900 params). MPS can represent correlations **across modes** through the bond connections, while CP at the same parameter count can only represent a sum of rank-1 terms with no inter-mode interaction. MPS's inductive bias — that information propagates locally between adjacent modes — turns out to match the structure of this Q-function well.

The tabular CP (`cp_agent`) is also genuine tensor decomposition for the same reason: the Q-table is a true 3-mode tensor `Q[row, col, action]`, so factorizing it with CP exploits the multi-linear structure across all three axes simultaneously. It's arguably more honest than CPLinear, which just happens to be called CP.
